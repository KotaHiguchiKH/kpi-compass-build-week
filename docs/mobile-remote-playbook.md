# スマホから Claude Code を使う運用ガイド(実測版)

作成: 2026-09-20 / 更新: 2026-09-20(ローカルPCセッションで `/rc` 側を実測)
検証セッション(クラウド側): https://claude.ai/code/session_01BACw9VgziGecBeDcd8U5PG
検証方法: (1)iPhone から起動したクラウドセッション内、(2)Windows ローカルの Claude Code セッション内、
の両方で実際にコマンドを実行して確認した。「実測」= どちらかで確認済み。
「公式doc」= 未実行、Claude Code ドキュメント記載。

## 結論

**主経路は Remote Control で、これは既に稼働している。** 2026-09-16 時点で
「Enable remote control by default」がこの PC でオンになっており(`kota_最新.md:800`)、
2026-09-20 の実測で RC 有効セッションが 8 本生きていることを確認した。
毎朝セッションを立てる、といった準備は要らない(→ 6節)。

クラウドセッションは保険。リポジトリの中で完結する作業は、スマホからでも普段どおりに回る。
落ちるのは「PC のローカル環境そのもの」に依存する作業だけで、その境界は明確に引ける。

- 回る: コード変更・テスト実行・調査・Web検索・Gmail/カレンダー/Drive参照・
  GitHub Issue 起票・MD への記録・コミット/プッシュ/PR・PR の CI 追従
- 落ちる: PC のファイル(リポジトリ外)、ローカルのアプリ操作、ブラウザ実操作、
  `~/.claude/CLAUDE.md` の個人メモリ
- 最大の落とし穴: **個人メモリ `~/.claude/CLAUDE.md` はクラウドに同期されない**(実測)。
  記憶を効かせたいなら、置き場をリポジトリ側に移す必要がある(後述)

## 1. 「スマホから」には別物が2つある

混同すると判断を間違えるので先に分ける。

| | クラウドセッション(このガイドの対象) | Remote Control (`/rc`) |
|---|---|---|
| 実行場所 | Anthropic のクラウドVM | 自分の PC |
| PC の状態 | **落ちていてよい** | 起動＋`claude` プロセス常駐が必須 |
| 見えるファイル | GitHub から clone したリポジトリのみ | PC のファイル全部 |
| 個人メモリ `~/.claude/CLAUDE.md` | **届かない**(実測) | 効く |
| ローカル MCP / ローカル設定 | 届かない | 効く |
| 起動 | Claude アプリの **Code タブ** | **不要**。Desktop アプリの既定でオン(実測) |
| 向く場面 | 手元にスマホしかない / PC が落ちている | PC は動いているが手元はスマホ |

出典(公式doc): https://code.claude.com/docs/en/claude-code-on-the-web ,
https://code.claude.com/docs/en/remote-control

**使い分けの既定値**: PC が起きているなら Remote Control が上位互換で、かつ **既定で有効**。
PC が落ちているときだけクラウドセッション。「PC を起こしに行けない」ケースへの備えとして
クラウドセッション単体で完結できる状態を作る案は、2026-09-20 に**不採用**とした
(Issue #276、→ 6節)。kota-md は RC 経由で届くため、GitHub へ置く理由が無い。

## 3. 記憶をスマホから効かせる方法

クラウドセッションに `~/.claude/CLAUDE.md` は届かない。したがって
**「クラウドセッションにとっての記憶 = リポジトリにコミットされたファイル」** になる。

効く置き場は3つ。上から優先度が高い。

1. `<repo>/CLAUDE.md` — 毎セッション自動で読み込まれる。運用ルールの本体
2. `<repo>/AGENTS.md` — 同上(他ツール互換)
3. `<repo>/docs/*.md` — 明示的に参照させる補助資料(このファイル)

現状の問題(2026-09-20 実測):

1. このリポジトリの `CLAUDE.md` には「正本は `~/.claude/CLAUDE.md` の ai-todo 節。
   齟齬があればそちらが優先する」と書かれているが、**クラウドセッションからは
   その正本が読めない**。コピーがドリフトしても検知できない
2. 個人ナレッジの `kota-md` は GitHub に無い(実測: `git remote -v` が空・762コミットすべてローカル)。
   つまり **自己分析・過去の決定・就活の文脈はクラウドセッションから参照できない**

   **リポジトリの見え方は実行環境ごとに違う(2026-09-20、両側で実測)**:
   GitHub アカウントが2つあり、**ローカルの `gh` とクラウドセッションでは見えるリポジトリが違う**。

   | 実行環境 | 認証アカウント | 見えるリポジトリ |
   |---|---|---|
   | ローカル PC の `gh` | `higuchi-kota`(id 277040382) | `KotaHiguchiKH/kpi-compass-build-week`(public)、`higuchi-kota/kaien-privacy-policy`(public) |
   | クラウドセッション | `KotaHiguchiKH`(id 190890880) | `KotaHiguchiKH/kpi-compass-build-week`(public)、**`KotaHiguchiKH/yosoku`(private・push可)** |

   本ガイドの一時的な版に「`yosoku` は存在しない」「private リポジトリは1つも無い」と
   書いたが、**どちらも誤り**。GitHub API(`owner:KotaHiguchiKH`)で
   `yosoku` は `private: true` / 権限 admin・push として実在が確認できた
   (2026-09-20、クラウドセッションから照会)。ローカルの `gh` に見えなかったのは、
   `yosoku` の所有者が `higuchi-kota` ではなく `KotaHiguchiKH` だからで、
   リポジトリが無いからではない。

   **運用上の含意**: スマホから `add_repo` で引き込める範囲は、PC で
   `gh repo list` を叩いた結果とは一致しない。どちらか一方だけを見て
   「無い」と判断しないこと。
3. この結果、スマホから投げられるのは「このリポジトリの文脈で完結する作業」に限られる。
   例えば「自己分析(#233)を踏まえてESの下書きを作る」は、
   ローカルなら通るがクラウドセッションでは材料が無い

→ **決着(2026-09-20、Issue #276 クローズ)**: 置き場は動かさない。理由は3つ。
(1) kota-md へは Remote Control 経由で届く(主経路がそちらに確定した)、
(2) バックアップは `PC-Backup-Daily` が毎日13:00に `H:\マイドライブ\PCバックアップ\kota-md` へ
退避済み(実測: 最終実行 2026/09/20 13:00・結果0・300ファイル)、
(3) このPCの `gh` トークンは `repo` フルスコープのため、private 化は公開範囲を
「GitHub上の誰か」から「このトークンに触れる全AI実行環境」へ移すだけで、割に合わない。
kota-md にリモートを置かないのは既決事項でもある(`kota_archive.md:1329`)。

### 他リポジトリを引き込む方法(判断が出るまでの暫定)

セッション中に `add_repo` でリポジトリを追加できる。GitHub 上にあるものに限る。
クラウドセッションから引き込めるのは `KotaHiguchiKH` 配下、すなわち
`kpi-compass-build-week` と `yosoku`(private)。`higuchi-kota/kaien-privacy-policy` は
別アカウント所有のため、このセッションのリポジトリ一覧には出てこなかった。

なお **この訂正は Issue #276 の決着(案C)を覆さない。** 案C の根拠は
(1) RC が既に稼働していること、(2) バックアップが既にあること、
(3) `gh` トークンが `repo` フルスコープであることの3点で、
private リポジトリの有無はいずれの支えにもなっていない。
むしろアカウントが分かれている分、「private に置けばクラウドから読める」も
自明ではない(所有アカウントが違えば読めない)。

## 4. スマホからの投げ方(実用テンプレ)

音声入力で長く喋っても通る。構造化はこちら側でやる。最低限これだけ含める。

```
【やること】<動詞で1行>
【対象】<リポジトリ名 / ファイル / Issue番号>
【終わり方】<コミットまで / PRまで / 調査結果を報告だけ>
```

タスク種別ごとの推奨:

| やりたいこと | スマホからの出し方 |
|---|---|
| コード修正 | そのまま投げる。「PRまで」と書けばドラフトPRまで到達する |
| 調べもの | 「調べて docs/ に MD で残して」と付ける。チャットだけだとVM回収で消える |
| 会話の記録 | 「この会話を docs/ に MD で残して」。→ コミットされるので次回以降も読める |
| 記憶に残す | 「CLAUDE.md に追記して」。個人メモリではなくリポジトリ側に入る |
| ai-todo 起票 | いつもどおり。ラベル `ai-todo` 付き Issue が立つ |
| PR の面倒見 | 「このPRのCIを見て直して」。イベント購読して自動で追従する |
| PC の操作が要る作業 | **投げない**。`/rc` に回すか、ai-todo Issue にして手元でやる |

### 落ちないための注意

- **チャットの出力だけで終わらせない。** VM は無活動で回収される。残したいものは
  必ず「ファイルにしてコミットして」まで言う(このリポジトリは Stop フックが
  未コミットを検出するので、ほぼ自動で守られる)
- 長時間タスクはアプリを閉じてよい。セッションはクラウドで走り続ける(公式doc)
- プッシュ通知を受けたいなら iOS の Focus / 通知要約でブロックされていないか確認
  (設定 → 通知 → Claude)(公式doc)
- 途中で質問されたまま放置するとVM期限切れになりうる。再度開けば会話履歴は復元される(公式doc)

## 5. Remote Control の実測(2026-09-20、ローカルPCセッション)

公式doc だけを根拠にしていた部分を、このPCで実際に確認した。

### 5.1 実測できたこと

| 項目 | 実測結果 | 確認方法 |
|---|---|---|
| RC は有効か | **有効**。このセッションが `remoteControlState: "on"` | セッションのメタデータ |
| RC 有効セッション数 | **8本**(2026-09-20 時点) | セッション一覧 |
| 毎回の起動コマンド | **不要**。既定でオン(`ccRemoteControlDefaultEnabled: true`) | `kota_最新.md:800`(2026-09-16) |
| Claude Desktop の自動起動 | **あり**。`HKCU\...\CurrentVersion\Run\Claude` に登録済み | レジストリ |
| AC 電源時のスリープ | **しない**。`STANDBYIDLE` AC=0 / `HIBERNATEIDLE` AC=0 | `powercfg /query SCHEME_CURRENT SUB_SLEEP` |
| バッテリー駆動時 | 20分でスリープ、120分で休止(DC=0x4b0 / 0x1c20) | 同上 |
| スリープの種別 | S0 低電力アイドル(Modern Standby)。**ネットワーク接続を維持** | `powercfg /a` |
| 再起動の頻度 | 過去5日で **7回**(9/15×3, 9/16, 9/17×2, 9/18)。大半は手動 | イベントID 1074 |
| Windows Update の強制再起動枠 | アクティブ時間 9:00〜3:00 のため **3:00〜9:00 のみ** | `HKLM\...\WindowsUpdate\UX\Settings` |
| `claude remote-control` CLI | 存在する。`-c/--continue` は「約4時間以内」の記録が必要 | `claude remote-control --help` |
| RAM への影響 | claude プロセス21本で **3.58GB** / 物理15.7GB・空き4.3GB(使用率72%) | プロセス一覧 |

### 5.2 「4時間ルール」は実務上ほぼ効かない

`claude remote-control --continue` の約4時間制限は、**ターミナルで単独起動した RC サーバ**の話。
このPCの主経路は Desktop アプリの既定ONなので、再起動後はログオン時に Claude が自動起動し、
セッションは一覧から選び直せる。4時間を数える運用は発生しない。

**ただし再起動をまたぐとセッションの「続き」は切れる。** 会話の継続性は
`docs/` の MD・git 履歴・kota-md が担う(既決方針)。

### 5.3 まだ未検証なもの

- **プッシュ通知が実際に iPhone に届くか**。設定の所在は公式doc で確認できるが、
  実到達はオーナーの端末でしか確かめられない
- **ネット断10分超でセッションが死ぬか**。公式doc と `kota_archive.md:1350` に記載があるが、
  意図的に回線を落とす検証はしていない
- `--teleport`(クラウド→ターミナル引き継ぎ)
- Claude Desktop のウィンドウを閉じた場合に RC が維持されるか

## 6. 運用の結論(2026-09-20 確定)

### やること: 何も新設しない。是正を2つだけ

**1. RC 有効セッションを溜めない。**
RC がオンのセッションは作業が終わってもプロセスが残る(`md差分ログ.md:921`、および今回の実測で
RC 8本 / claude 21プロセス 3.58GB を確認)。物理15.7GBに対し空き4.3GBまで詰まっている。
**用が済んだセッションはサイドバーでアーカイブする。** スマホ用の常設1本だけ残せばよい。
「既定RCオンをオフにする」案は採らない(スマホ操作そのものを失うため)。

**2. リポジトリ側 `CLAUDE.md` / `AGENTS.md` の ai-todo 節を正本と同期する。**
→ 本コミットで実施。詳細は 7節。

### やらないこと

| 案 | 却下理由 |
|---|---|
| 毎朝 `claude remote-control` を立てる運用 | **不要**。既定でオン・ログオンで自動起動(実測)。ADHD特性に対して最も良いのは「何もしなくていい」こと |
| kota-md を GitHub private repo へ | Issue #276 でクローズ。→ 3節 |
| クラウドセッションでローカル同等を再現 | オーナー判断で保留済み |
| スリープ設定の変更 | AC電源時は既に無効。変更不要 |

### 塞がらない穴(構造的に残る)

| 穴 | 対処 |
|---|---|
| PC の電源断・シャットダウン | **対策しない**(既決・`kota_archive.md:1321`)。落ちている日はクラウドセッションへ |
| ネット断10分超でセッション死 | 復帰後に立て直す。継続性はMD・git・kota-mdが担う |
| **Claude Code 自体の利用上限** | **自動フェイルオーバー不可能**(`kota_最新.md:501`)。Claudeが止まると切替判断の主体がいなくなるため。事前の Codex 委任だけが有効な対策 |

### 未ヒアリング

「AIとのつながりが失われるパターン」について、kota-md には**網羅的な列挙が存在しない**。
個別記録から拾えたのは以下7件で、これはオーナーが列挙した原文ではない。

1. 移動中(→ テザリングで解消済み・2026/08/20)
2. 滞在先で意思決定が止まる(→ Drive `外出中メモ.md` 経路で対処)
3. ターミナルUIでは生産性が出ない(→ SSH経路は非常用予備に降格)
4. **利用上限**(→ Claude側は構造的に塞げない)
5. PC電源断・スリープ・セッション死
6. 回線障害(自宅Wi-Fi・DNS)
7. アカウント/権限側の事故

**残りのパターンはオーナーへの聞き取りが必要。**

## 7. ai-todo 節の齟齬(2026-09-20 実測・本コミットで修正)

クラウドセッション側の宿題「正本とリポジトリ側コピーに齟齬があるか」の答えは **あった**。
しかも齟齬の種類が2段階ある。

### 7.1 正本へのポインタ自体が壊れていた

リポジトリの `CLAUDE.md` は「正本は `~/.claude/CLAUDE.md` の『ai-todo』節」と書いていたが、
**`~/.claude/CLAUDE.md` に ai-todo 節は存在しない。** そのファイルは索引表の1行
(「オーナー本人の行動が必要 → Issue起票・棚卸し | `ai-todo` スキル」)を持つだけで、
実体は `~/.claude/skills/ai-todo/SKILL.md` に移っている。
クラウドセッションが「正本が読めない」と報告したのは正しいが、
**ローカルから読んでも同じ場所には無かった。**

### 7.2 内容の欠落(正本にあってリポジトリ側に無いもの)

| 規則 | repo `CLAUDE.md` | repo `AGENTS.md` | 正本(スキル) |
|---|---|---|---|
| 納得ゲート | あり | **無し** | あり |
| 起票前ゲート(顔見知りへの確認は先にオーナーへ聞く) | **無し** | **無し** | あり |
| 完了報告の要否は Claude が決める(2026-09-16決定) | **無し** | **無し** | あり |
| 作成後に `gh issue view <n> --json labels` でラベル確認 | **無し** | **無し** | あり |
| Claude が代行完了したら即 close | **無し** | **無し** | あり |
| 締切48時間以内はカレンダー通知を併用 | **無し** | **無し** | あり |
| `ai-todo-verify.tsv` への登録 | **無し** | **無し** | あり |

このうち**実害が確認されているのはラベル確認の欠落**。`gh issue create -l ai-todo` は
ラベル付与に失敗しても URL を返して成功に見えるため、付かないと ai-todo 一覧に出ず、
オーナーに実質届かない。クラウドセッションはリポジトリ側の記述しか読めないので、
この抜けはそのまま事故につながる。

本コミットで両ファイルを正本に合わせた。
