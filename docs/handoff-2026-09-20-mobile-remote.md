## 1. 状況

オーナー(Kota)のボトルネックは「AI とのつながりが失われた時に作業が止まること」。
そのパターンの1つが「手元にスマホしかなく、ローカルで作業できない時」。
この経路が実用になるかが未検証のまま使われていなかったため、
2026-09-20 に iPhone 起点のクラウドセッションで実測した。

実測の結論は `docs/mobile-remote-playbook.md`(PR #275)にある。
そのうえでオーナーから次の判断が示され、引き継ぎに至った。

> スマホ起点のセッションでローカルと同じことができる環境を作るのは負担が大きい。
> 簡単ならやりたいが、そうでないなら「PC で先にセッションを立てておき、
> 電源と Claude Code を繋いだ状態でスマホから話しかける」方が現実的ではないか。

この判断を、ローカルにしかない文脈(個人メモリ・kota-md)も踏まえて検証してほしい。

## 6. 次のタスク(このローカルセッションでやること)

1. `~/.claude/CLAUDE.md` を読む。ai-todo 節の「正本」と、
   リポジトリ側 `CLAUDE.md` のコピーに**実際に齟齬があるか**を確認する
2. `kota-md` を読む。特に次を探す
   - 「つながりが失われるパターン」に関する過去の記述(残り N 件のパターン)
   - 音声入力の障害に関する過去の記述
   - 作業環境・ワークフローについて既に決まっている方針
3. `/rc` を**実際に起動して検証**する(公式doc のみが根拠の部分を実測に変える)
   - Windows のスリープ設定で落ちないか
   - プッシュ通知が実際に iPhone に届くか
   - PC 再起動後に4時間ルールが実務上どう効くか
4. 上記を踏まえ、**全体最適な運用**を1つ提案する。評価すべき軸は最低限これら

   | 軸 | 問い |
   |---|---|
   | 事前準備の要否 | `/rc` は「PC を事前に用意しておく」ことが前提。用意を忘れた/出先で急に必要になった時にゼロになる。その頻度は? |
   | 常駐の安定性 | Windows Update の再起動、スリープ、ネット断をまたいで生き残るか |
   | 習慣化コスト | 毎朝 `claude remote-control` を立てる運用は ADHD 特性と噛み合うか。自動起動にすべきか |
   | バックアップ | `kota-md` はローカルのみ。PC 故障で消える。これは経路の話と独立したリスク |
   | 公開範囲 | `kpi-compass-build-week` は public。個人情報を含む ai-todo Issue が既に入っている |

5. Issue #276 `[要相談]`(kota-md の置き場を A/B/C から選ぶ)に、
   ローカルの文脈を踏まえた**推奨を1つ**コメントする。
   前提が変わって不要になったならクローズする
6. 判断が確定したら `docs/mobile-remote-playbook.md` を更新し、
   `[未検証]` を `[実測]` に置き換える

## 7. 出力形式

オーナーの指定に従うこと(`~/.claude/CLAUDE.md` の指定が優先)。最低限:

- **結論から書く**。推奨は1つに絞り、「主推奨」を明示する
- 推奨には「**この案が外れるならどこか**」を1行添える。ただし述べたら作業は止めず続行
- 判断依頼は「結論 → 判断を左右する軸 → 案ごとの評価」の順。軸の比較は**表**
- 「未確定」「未検証」を明記する。「〜のはず」を根拠にしない
- 確認質問は最小限。前提が不明なら仮定を明示して進め、**末尾に仮定一覧**を置く
- 本人にしかできない作業が出たら、その場で ai-todo Issue を起票する
  (納得ゲートを通す。オーナーが是非を判断していないものは `[要相談]`)
